# 本地胜率分析

## 搜索与概率分开

`win-probability.ts` 保留 v0.1 的随机启发式策略及估计器，作为冻结对照。
`tactics.ts` 穷举有限战术窗口，覆盖立即胜利、技能、额外回合、付款和弃币。
预算用尽、未知补牌或盲抽返回 unknown，不当作必胜或必败。

`search.ts` 实现 PUCT 选择：利用均值，加上先验乘以父节点访问量平方根、
再除以子动作访问次数的探索项。每次迭代重新采样未来牌库与袋中筹码；
不同实际揭示结果形成不同子节点。节点按实际行动方计算价值，不能按深度
简单正负交替，因为同一玩家可能连续行动。

`search-policy.ts` 整合战术与搜索。对战评测每步 24 次搜索；
回放续弈每步 8 次搜索、树深上限 6、内部随机 rollout 深度为 0，
非终局叶子用手写的胜利进度、经济、资源潜力估值。小预算可能只搜索到浅层，
不是完整求解，也没有策略网络或价值网络。

显示概率来自**外层完整续弈的实际胜负**。树中访问比例和叶估值不作为概率。
未完成的模拟单列，并扩大抽样区间；不能把它们当成平局或失败。
未知牌库排序、原始 RNG、之后的真实行动不进入预测，但局后复盘会使用双方
在该步已持有的预留牌，因此不是某位玩家当时的隐藏信息信念模型。

## 渐进分析与默认回退

`match-analysis.ts` 是对局与回放共享的唯一调度器。对局期间默认后台计算两种
策略，菜单可关闭；结果只在终局回放中展示。`progressive.ts` 继续累计固定
8、24 次里程碑和可选单步 64 次预算，每个工作批次最多增加 2 次样本。
当前局面与历史待办交替获得预算，避免快速走步让旧局面一直无法计算；
回放选中的步骤优先。后台结果按对局与策略分开保存，终局直接复用。

同一页面全局至多一个分析 Worker、一个在途任务。只传一个无日志的局面；
待办由行动记录的索引与计数推导，不排队存储完整快照。`ReplayWindow`
按需重建历史，每个协调器缓存最多 4 个快照，打开回放后另有最多 4 个显示缓存。
查看归档时，当前协调器暂停但保留缓存，额外挂载一个历史协调器，因此最多 12 个缓存快照。
每个协调器的数字估计最多两种策略各 5001 条，受现有 5000 步对局上限约束；换局或导入
会释放旧运行缓存，再加载匹配的已存样本。搜索树在单次决策结束后即可回收，不跨步保存。

后台每次续弈后休息约等于该次计算的时长，目标约占一个逻辑核一半时间；
回放前台取消该休息。动画忙碌、页面隐藏、关闭预计算且未查看回放时，直接
终止 Worker，保留已完成计数；空闲完成后也释放 Worker。重开或恢复时按
样本编号继续，不重复累计。关闭回放后若预计算仍开启，会恢复后台节流。
以上是应用持有量与调度边界，不是浏览器总内存或 CPU 的硬限制。

## 持久化与历史回放

v0.3 在 `MatchRecord.analysis` 中保存两种策略的紧凑样本计数：步骤、16 位十六进制
局面校验键、双方胜场、未完成次数和 24／64 次目标，并记录策略版本 ID。
概率及区间不作为可信输入保存；刷新或导入后，先核验格式、策略版本和对应局面，
再由计数重新计算。无效或不兼容的分析缓存可丢弃重算，不妨碍合法对局继续使用。
已完成样本沿用同一编号序列，未完成目标继续累计，不重新计入旧样本。

分析持久化以约 1 秒节流写入，并在 `pagehide` 或页面隐藏时尝试立即保存。
强制结束进程、浏览器崩溃或存储失败仍可能丢失最近尚未写入的样本；
因此“可续算”不等于每个瞬间都已落盘。导出的对局 JSON 一并携带兼容的样本计数。

已完成对局另存入本应用的历史归档，最多最近 5 局，整个归档 JSON 的 UTF-8
大小上限为 1,500,000 字节；超限时淘汰较旧记录，单局过大则不能加入归档。
单份对局 JSON 仍受 2,000,000 字节上限约束。上述是序列化数据限制，
不是浏览器实际磁盘占用保证。历史回放使用选中的归档，不覆盖当前正在玩的对局；
分析仍遵循单 Worker 限制，不因打开历史而增加并发。
升级前已经覆盖的对局无法追溯，重要对局应及时导出备份。

## 估计边界

单点 Wilson 95% 区间只描述给定模拟策略下的抽样误差，不包含策略偏差，
也不保证反复查看或整条曲线同时覆盖。系统不按区间宽度自适应停止。

验收中搜索策略棋力显著改善，但 Brier 与 LogLoss 未优于基线。
所以 UI 默认仍是快速基线，搜索作为可选复核，不能把它宣传成已校准的升级概率。
要继续改善概率，需要更多独立且接近目标玩家水平的对局，再做按整局分割的
校准与保留集评估；仅增加 MCTS 或模拟次数不能消除策略偏差。

## 与围棋 AI 的关系

共同点是树搜索、探索与利用、回传价值。这里采用手写先验和叶评价，
没有 AlphaZero 式自我对弈训练的深度网络；此外还必须处理随机补牌、
预留信息及连续行动。因此不能把此实现等同于 AlphaGo/AlphaZero。

## 使用成本

没有模型 API 调用、训练、运行时 token 费用或 GPU 要求。
当前瓶颈是单 Worker 中反复复制规则状态、生成动作及运行搜索，主要消耗 CPU。
Ryzen 7 8845H 验收中每个中盘局面 24 次续弈，快速基线平均 0.270 秒，
搜索平均 9.807 秒。不同阶段差异很大，完整回放的搜索可能需要数分钟。
这是 Node 测试耗时，浏览器和低功耗设备可能更慢；不是所有设备的延迟保证。
已在约 31 GiB 主机上验证，未建立最低内存配置，不能声称低内存设备均已验证。
保留浏览器架构；改为 EXE 本身不会减少搜索工作量。

新增后台模式实测（2026-11-13）：一个 Node Worker 对开局执行 24 次搜索续弈，
启用等时休息后用时 23.18 秒，全部完成。每次完成采样处观测到的 Worker JS 堆
最大 29.41 MiB。此测量不包含浏览器、图像/GPU、Worker 之外的内存，也可能
遗漏采样点之间的瞬时峰值。原始记录见 [background-memory.json](benchmarks/background-memory.json)。
若人类走步快于分析，未完成局面会留待后续或终局继续，不能保证每局结束时全部已算完。
